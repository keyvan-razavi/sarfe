## Phase 2–4 functional acceptance scenarios

- A category defines a required select attribute and a numeric attribute. Valid variants save; an invalid select value and missing required value fail with an actionable message.
- Existing variants remain valid when a category is edited; incompatible changes are rejected or handled through an explicit migration.
- An owner creates a draft product, edits its variants, publishes it, and sees it in the matching public category. A draft does not leak through a direct product URL.
- Duplicate slugs/SKUs and negative stock/prices fail without partial writes. Category hierarchy cycles fail.
- Missing database configuration shows a labeled read-only preview. A failing configured database yields an error, never a successful mutation.
- A signed-out visitor cannot perform a CMS mutation even when invoking the action directly. Missing secrets cannot produce an authorized session.
- A shopper filters by category and search, selects an available variant, adds it, changes quantity within stock, refreshes, and sees consistent integer-money totals. A mixed-currency cart is rejected.
- All primary flows work at mobile/tablet/desktop widths in light and dark themes with keyboard-visible focus, in both Persian and Kurdish Sorani. Locale persists and server/client rendering agrees; category/product sample content is localized.

## Owner login throttling — November 15, 2026

Owner sign-in now persists a shared throttle row in PostgreSQL. Five failed attempts trigger a 15-minute lock; lock state is checked before password verification and rechecked while holding a row lock before resetting failures after valid credentials. Database errors fail closed; no email/IP or credential data is stored. The migration has been applied to both the dedicated `sarfe_store_test` database and local `sarfe_store` app database. The production build issue described here was resolved in the November 16 follow-up below.

## Customer checkout foundation — November 16, 2026

The cart now links to a Persian/Sorani `/checkout` page with customer contact and Iran delivery fields. `/api/checkout` accepts only customer/address details plus variant IDs and quantities, checks request origin and JSON size, and uses the existing PostgreSQL order service to reload published variants, prices, and stock, reserve inventory transactionally, and return the server-calculated total and expiry. Due reservations are opportunistically released before a new checkout request. The client cart never supplies authoritative money or product data. No payment is taken. Checkout stays unavailable until the owner supplies explicit server-only policy ID, currency, fixed shipping/tax amounts, and policy labels; production additionally requires `CHECKOUT_ENABLED=true`. The fixed-amount policy is an implementation seam, not an approved tax/shipping rule. Payment processing, abuse controls, full browser review, verified pricing policy, and operational expiry scheduling remain pending.
